# S2.R2 — HEIC/HEIF metadata: structure, bounded reading, recommendation

> **Task:** S2.R2 (Stage 2, research; documentation only). **Date:** 2026-09-26.
> **Repository:** `main` @ `1b39a7c`. No application code changed.
> **Status: evidence complete for the owner's sample. Owner decision pending (§8).**
> Facts are marked **[verified]** (with the evidence), **[unknown]** (with what would resolve
> it), or **[assumption]**.

## 1. Question

Can the metadata contract (ADR-017 §2) be read from HEIC/HEIF files in a bounded way,
through the shared EXIF extractor (ADR-017 §13), without decoding images? If so, how, and
with which limits?

## 2. Constraints

- **ADR-017:**
  - bounded reads within a byte budget;
  - no image decoding;
  - GPS, serials and observer identity are never extracted;
  - no inferred time zone;
  - I/O in the data layer;
  - support only with a real sample and tests.
- **ADR-017 §13:** a HEIF reader is a container reader over `ExifStructure` and
  `MetadataSourceWindow`, and the contract stays unchanged.
- **Android:** the document channel reads in place. Positioned reads work on seekable
  descriptors; a descriptor that cannot seek is read from the start, within the 1 MiB budget
  only (S2.4).

## 4. Verified facts

1. **Locating the Exif item is cheap and bounded:** the `meta` box is 3.2 KB at the start.
2. **Reading it needs random access.** The Exif item sits at the end of the file (97 % in).
   A positioned read reaches it with a few KB. Reading sequentially from the start would take
   about 1.9 MB, over the 1 MiB budget, so on a non-seekable provider the reading is
   `MetadataUnreadable(overBudget)`: typed and honest, never partial.
3. **The `exif_tiff_header_offset` must be honoured.** Here it skips a JPEG-style APP1 header.
   Assuming the TIFF header right after the 4 bytes would fail.
4. **The Exif item is identified by `iref cdsc` pointing to the primary item.** Picking "the
   first Exif item" would work here, but not with multi-image files.
5. **The EXIF inside is the same structure `ExifStructure` already reads** (S2.3/S2.7), so no
   contract change is needed.
6. **Stage 3 evidence (RG-02).** The same phone writes different identity strings by format:

   | | Model | UniqueCameraModel |
   | --- | --- | --- |
   | DNG | `Xiaomi 14T Pro/2407FPN8EG` | `2407FPN8EG-Xiaomi-Xiaomi` |
   | JPEG and HEIC | `Xiaomi 14T Pro` | — |

   Matching must not rely on exact Model equality across formats.
7. **Time zones differ by format.** The phone's JPEG and HEIC record `OffsetTimeOriginal`;
   its DNGs do not. The same device therefore gives a UTC instant from one format and "zone
   unknown" from another, which ADR-017 §3 already handles.

| Option | For | Against |

| **A. ## 7. Recommendation

**Option A**, as S2.9:
1. Walk the top-level boxes: `ftyp` (already recognised), then `meta`. Refuse a `meta` box
   over **64 KiB**, or one that does not come before `mdat`'s payload is needed. Use 64-bit
   box sizes when present.
2. In `meta`, read `pitm`, `iinf`/`infe` (versions 2–3, item type `Exif`), `iloc` (versions
   0–2; **construction method 0** (file) and **1** (`idat`); method 2 refused, typed), and
   `iref` `cdsc`.
3. **Choose the Exif item linked by `cdsc` to the primary item.** If none is linked and there
   is exactly one Exif item, use it. If there are several and none is linked, read each and
   `MetadataValue.combine` them, so differing values stay **ambiguous**, never guessed.
4. Read the 4-byte `exif_tiff_header_offset`, check that it lies inside the extent, and hand
   the rest to `ExifStructure` as a `MetadataSourceWindow` (container label `Exif item`).
5. Never read `mdat` beyond the Exif extent, and never decode or touch the image items.
6. **Fixtures:** synthetic ISO-BMFF built in code (meta variants; Exif before and after
   `mdat`; the offset prefix; truncated, looping and oversized boxes; several items). The
   owner's HEIC goes into the local real-sample check. **Acceptance:** the owner's HEIC gives
   the contract values within the budget, from a few KB of reads.
