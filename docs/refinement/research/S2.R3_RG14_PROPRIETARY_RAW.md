# S2.R3 — RG-14: proprietary RAW compatibility and libraries

> **Task:** S2.R3 (Stage 2, research; documentation only). **Date:** 2026-09-26.
> **Repository:** `main` @ `237c55f`. No application code changed.
> **Status: evidence complete; owner decision pending (§8).**
> Facts are marked **[verified]** (with a source), **[documented]** (by a reverse-engineering
> source, not an official specification), **[unknown]**, or **[assumption]**.

## 1. Question

Can the metadata contract (ADR-017 §2) be read from proprietary RAW files (CR2/CR3, NEF,
ARW, RAF, RW2, ORF) without ad hoc parsers, without image decoding, and within ADR-017's
bounded-read, privacy and licence rules? If so, through which library, platform facility
or container adapter? (RG-14; DECISIONS E.1, "Stage 2 format priorities".)

## 2. Constraints

- **Owner (2026-09-26):**
  - no ad hoc RAW parsers now;
  - no image decoders or universal RAW framework;
  - no support claimed without a real sample and tests;
  - RAW, DNG and JPEG are the primary focus.
- **ADR-017:**
  - bounded reads within a per-file budget (§4), with I/O in the data layer;
  - GPS, serials and observer identity never extracted (§3);
  - typed values with provenance, with conflicts kept visible (§5);
  - one shared EXIF extractor behind container readers (§13).
- **Licence:** the app is GPL-3.0 (PD-12).
- **Current state:** CR2, CR3, RAF, RW2 and ORF are recognised by signature. NEF and ARW
  are recognised as plain TIFF; without DNGVersion they are `MetadataUnsupported(tiff)`.
  **No real sample of any proprietary RAW exists** (the owner's samples are phone DNG, JPEG
  and HEIC).

## 3. Evidence

### 3.1 AndroidX `ExifInterface` (platform library candidate)

From `developer.android.com/reference/androidx/exifinterface/media/ExifInterface`, fetched
2026-09-26 **[verified]**:

- "Supported for reading: JPEG, PNG, WebP, HEIC, DNG, CR2, NEF, NRW, ARW, RW2, ORF, PEF,
  SRW, RAF, AVIF (on API 31+)". **CR3 is not listed.**
- Constructors take a `FileDescriptor` (since 1.1.0), a `File`, a path or an `InputStream`.
  The documentation states **no bound on how much of a file is read**, nor whether a
  non-seekable stream is read in full.
- It exposes values as string attributes (`getAttribute`) and parses GPS itself
  (`getLatLong`).
- Its licence: **[assumption]** Apache-2.0, like other AndroidX libraries, to be confirmed in
  the artifact's POM before any use.

### 3.2 LibRaw (native library candidate)

From `libraw.org/about`, fetched 2026-09-26 **[verified]**:
- licensed under LGPL-2.1 or CDDL-1.0;
- a C/C++ library that extracts "RAW data (pixel values)" and processing metadata, plus
  embedded previews.

It is a RAW decoding library.

### 3.3 Where each format keeps the contract's values

| Format | Structure | Source | Reachable in a bounded way with the shared extractor? |
| --- | --- | --- | --- |
| **CR2** | A TIFF with `CR` and version 2 at byte 8; IFD0 holds Make/Model and the EXIF IFD pointer | **[documented]** (reverse engineering; the signature is already implemented, S2.7) | Likely yes: the same `ExifStructure` at offset 0. **[unknown]** until a sample |
| **NEF, ARW** (also PEF, SRW) | Plain TIFF (`II*\0`/`MM\0*`); IFD0 with an EXIF IFD; raw data in sub-IFDs | **[assumption]**, widely documented | Likely yes, as for DNG, but they are **not distinguishable by signature**: the maker needs IFD0 `Make` (level-1 recognition would read one tag) |
| **ORF** | TIFF layout with a non-42 magic (`IIRO`/`IIRS`/`MMOR`) | Signature implemented (S2.7); layout **[assumption]** | Likely, if `ExifStructure` accepts the ORF magic |
| **RW2** | TIFF-like, magic `0x55` (`IIU\0`), IFD0 with an EXIF IFD | Signature implemented; layout **[assumption]** | Likely, with the RW2 magic accepted |
| **RAF** | Big-endian header: magic `FUJIFILMCCD-RAW `, and at offset 0x54 the **embedded JPEG's offset and length**; EXIF lives in that JPEG's APP1 | **[documented]** (libopenraw, `libopenraw.freedesktop.org/formats/raf/`, fetched 2026-09-26) | Yes: a header read, then the existing **`JpegMetadataReader` on a window** |
| **CR3** | ISO-BMFF: `ftyp crx `, then `moov` right after (offset 0x18), with a Canon `uuid` box holding **CMT1** (IFD0 as a TIFF structure), **CMT2** (the EXIF IFD), CMT3 (maker notes) and **CMT4 (GPS)** | **[documented]** (Laurent Clévy, `github.com/lclevy/canon_cr3`, fetched 2026-09-26) | Yes: a box walk like HEIF's, then `ExifStructure` on the CMT1 and CMT2 windows; **CMT4 never read** |

One more observation **[verified on the owner's phone files]**: the same device writes the
same EXIF values in its companion JPEG and HEIC as in its DNG (except Model and the time
offset, S2.R2 §4.6). Many cameras shoot **RAW+JPEG**, and the JPEG is already supported.

## 4. Verified facts (summary)

- A platform library exists that reads most TIFF-family RAWs and RAF (not CR3). Its
  documentation does not bound its reads.
- LibRaw is a decoder, dual-licensed LGPL-2.1/CDDL-1.0.
- For every listed format, the contract's values sit in **TIFF/EXIF structures** that the
  shared `ExifStructure` already reads (directly, through a window, or inside the embedded
  JPEG). This is documented, but not verified on a real file for any proprietary format.
- No proprietary RAW sample exists yet.

## 5. Unknowns

| Unknown | Resolves it |
| --- | --- |
| Which RAW formats the owner (and target users) actually shoot | The owner's answer (§8, question 1) |
| Whether each format's real files place the contract's tags as documented (CR2/NEF/ARW EXIF IFDs; ORF/RW2 magic; RAF's header; CR3's CMT boxes) | One real sample per format |
| `ExifInterface`'s read behaviour on a large RAW through a `FileDescriptor` or a non-seekable stream; its licence as shipped | Reading its source or POM, and device instrumentation. Only needed if option B is chosen |

## 6. Options

| Option | For | Against |
| --- | --- | --- |
| **A. Container adapters over the shared extractor**, one per format, each **only with a real sample**. For example: CR2/NEF/ARW as TIFF (IFD0 `Make` identifying the maker); ORF/RW2 by accepting their magic; RAF via its header and `JpegMetadataReader`; CR3 via its `uuid`/CMT boxes, never CMT4 | Reuses the one contract, provenance, privacy exclusions, budget and host tests (ADR-017 §13); **no decoding and no MakerNotes**; no new dependency; each adapter is small (RAF and TIFF-family), CR3 medium | Per-format fixtures and samples. CR3's and RAF's layouts come from reverse engineering. It needs the owner to agree that such adapters are **not** the "ad hoc parsers" the owner excluded |
| B. AndroidX `ExifInterface` behind the platform channel | Maintained by Google; broad coverage (not CR3); no parsing code of ours | Android only, so not host-testable (fakes only); **no documented read bound** (ADR-017 §4 cannot be enforced or proven); it parses GPS internally (against the spirit of §3); string attributes lose which IFD a value came from, so ambiguity detection is lost; a second extraction path beside the contract pipeline |
| C. LibRaw through FFI | The broadest coverage | A decoder (excluded by the owner); a native build per ABI; LGPL/CDDL obligations; size |
| D. No proprietary RAW support for now | Honest: recognition already names the format; RAW+JPEG and DNG are supported | RAW-only shooters get "not supported yet" |

## 7. Recommendation

1. **Now, and to close Stage 2: D.** Proprietary RAW stays recognised only, and the screen
   says "not supported yet".
2. **The approved path per format: A**, as sample-driven Tasks after Stage 2, cheapest
   first:
   - RAF (header + JPEG reader);
   - CR2/NEF/ARW (TIFF, IFD0 `Make`);
   - ORF/RW2 (magic);
   - CR3 last (reverse-engineered layout).

   Each needs one real sample and follows the S2.8/S2.9 pattern: synthetic fixtures, a local
   real-sample check, a device check.
3. **Reject B and C.** B cannot prove the byte budget or the privacy exclusion, and it splits
   extraction into two paths. C is a decoder.
4. Until then, a RAW-only user can export DNG, or shoot RAW+JPEG. This is a UX hint for when
   the feature becomes visible (Stage 3); nothing is added now.
