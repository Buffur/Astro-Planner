## 1. The questions

- **Q1 (RD-05, 08 §2, O3).** Does the user need to see a "Draft" stage, or is the planner simply
  "the plan I'm working on", with Save meaning something clear?
- **Q2 (RD-05, 08 §5, §8).** What do New, "+", Duplicate and Open mean? What does the user see after
  each?
- **Q3 (RD-05, UX-12, W1, V3).** Unsaved plans: are they listed, confirmed before being replaced,
  or cleaned up? Does a site change edit a saved plan?
- **Q4 (UX-04).** How does the planner show which plan, which night, and its state?
- **Q5 (RG-04 D4).** What happens the next day to a saved plan whose night has passed?
- **Q6 (RD-04, 08 §14, UX-24).** What does a new plan start with: the target, the rig, the example
  capture plan, and the first run?
- **Q7 (UX-13).** The copy the planner continues on after Start, and its card on Tonight. RG-04
  largely answers this; §3 records it.

## 2. Evidence

### 2.1 Current behaviour (CODE VERIFIED)

**One current session.**
- The planner edits one session at a time (`CurrentSession`).
- At launch it resumes the most recently updated open session (draft, planned or in progress)
  (`drift_session_repository.dart:484–494`; ADR-014 §3, "Current session"). Without one, it creates
  a draft (`session_plan_viewmodel.dart:103–133`).

**Autosave.**
- Every edit autosaves (`current_session.dart:111–131`).
- An edit to a saved (planned) plan returns it to `draft`, keeping its `plannedAtUtc`, so it
  reads "Planned, unsaved changes" (`drift_session_repository.dart:67`).

**Save.**
- Save makes the session `planned` and refreshes its plan snapshot (`current_session.dart:152–161`).
- The snackbar says "Session saved to Logbook!" (`home_screen.dart:342`).

**Night roll-forward.**
- A resumed session whose night has passed is shown on tonight's night; a future night is kept
  (`session_plan_viewmodel.dart:124–128`; TASK 11.4).
- This applies to a **saved** plan too: yesterday's planned session becomes the planner's current
  plan today, shown for tonight, and the next edit rewrites its night key.

**New.**
- It keeps the target and rig, and sets tonight and the example plan
  (`session_plan_viewmodel.dart:256–262`).
- It is on Tonight ("New session") and in the planner's app bar ("+").
- The "+" gives no message; the page changes in place.

**Duplicate.** A copy of the plan for a picked night; the original stays (`:265–269`). An
icon-only action in the planner's app bar.

**Open.** From a session's detail: "Open in planner" (a draft or planned session) or "Plan again
(copy)" (a completed, abandoned or legacy one) (`session_detail_screen.dart:383–400`).

**The guard (S1.6, S1.V3).**
- New, Duplicate and opening another session ask "Discard unsaved changes?" when the current plan
  has edits since it was created, opened or saved (`unsaved_plan_guard.dart:10–35`).
- Discard leaves the old draft in the database, unlisted.
- An untouched example draft never asks, and it too is left in the database.

**Listing.** Pure drafts are never listed in Sessions (`library_viewmodels.dart:153`; TASK 11.3).

**State display.**
- Tonight's card shows "Draft", "Planned", "Planned, unsaved changes" or "In progress".
- **The planner shows none** (UX-04): its title is "Session planner" (`home_screen.dart:47`).

**Defaults.**
- The target is the last chosen, else **M42**; the rig is the last chosen, else **the first saved
  rig**, which on a fresh install is the seed "ZWO ASI2600MC + example 72 mm f/5.6 refractor"
  (`session_plan_viewmodel.dart:111–115`).
- The first-run page lists them as the user's choices (`welcome_screen.dart:93–126`; UX-24).
- The capture plan starts as the example: L 100 × 60 s, darks 20 × 60 s, flats 20 × 2 s
  (`example_capture_plan.dart`), with an "Example plan" badge until the first block edit (TASK 4.4).

**Known edges.**
- **W1:** after a Duplicate of an edited plan, New does not ask in the same run, but would after a
  restart. The copy's night can be lost.
- **V3:** a site change on a saved plan turns it into "Planned, unsaved changes", but it does not
  count as unsaved while the app runs, so New does not ask.
- **TD-057:** the draft's night key lags a rollover until the next edit.
- **TD-058:** New, Duplicate and Open are outside the autosave chain; a very fast edit can land in
  the old draft.

## 3. What RG-04 changes for the lifecycle

- **Save now has a clear meaning:** "I intend to image this plan." A saved plan appears in the
  Logbook, and after its night it waits for a result (RG-04 D2–D4). That is a reason to keep Save
  explicit (§5, Q1).
- **Start leaves the primary path** (D1), so UX-13's second card with a refused Start goes away
  from the default flow. When the optional live mode starts the planner's current plan, the
  planner still moves to a copy (ADR-016 §10), and Tonight shows the run card plus the copy. The
  copy's card must not offer Start while a run is in progress; its wording is S4.R4's.
- **Yesterday's saved plan must not silently become tonight's plan** (Q5). Today it rolls forward,
  and the next edit rewrites its night, which would detach it from the night it is waiting a
  result for.

## 4. Constraints

- **No silent loss** (`IA_WIREFRAMES.md` §3; principle 8).
- **Autosave stays** (TASK 11.4).
- **ADR-014:**
  - one aggregate;
  - snapshots are immutable once taken;
  - completed sessions are frozen;
  - any change to Save's semantics or to the lifecycle is an explicit amendment, recorded by
    ADR-019 (S4.D).
- **Defaults are labelled as defaults** (principle 7), and nothing is presented as chosen that the
  user did not choose (UX-24).
- **One place per action where possible** (principle 6). The placement on screens is S4.R4's; this
  step decides the meaning.
- **Stage 4 writes no code.**

## 5. Options and trade-offs, per question

### Q1 — Draft and Save

| | L1 — explicit Save; "Draft" hidden as a word (**recommended**) | L2 — autosave *is* saving; no Save button | L0 — as today, plus a state label |
| --- | --- | --- | --- |
| **Model** | Draft stays internal. The user sees "Not saved", "Saved" or "Saved · changed". Save means "I plan to image this"; only saved plans go to the Logbook | Every plan with a target, rig and night is listed and counts as planned. "Draft" exists only for an incomplete plan. The snapshot is re-taken on every change | Unchanged, plus the planner shows the state |
| **Matches O3 / 08 §2** | Yes: no separate Draft stage, just the plan and whether it is saved | Yes, fully | Partly |
| **Fits RG-04** (the Logbook holds intended sessions awaiting a result) | **Yes** | Poorly: every plan tried becomes a Logbook entry, and "how did it go?" would fire for plans never meant | Yes |
| **Data model** | None. ADR-014 unchanged; wording only | ADR-014 §3–§4 amended (Save, snapshot timing); many more listed sessions | None |
| **Risk** | The user forgets to Save. Mitigated by the state label (Q4) and the guard (Q3) | Clutter; snapshots no longer mark a moment of intent | The jargon stays |

### Q2 — New, Duplicate, Open

- **New** (*a plan for something else*). Options:
  - (n1) as today: same target, rig and night rules, with the example plan;
  - **(n2, recommended)** keep the site and the rig, and ask for the target. The capture plan
    follows Q6;
  - (n3) completely blank.

  Rigs rarely change between plans, while targets do; n2 removes a step and presents nothing as
  chosen that was not.
- **Duplicate for another night** (*the same plan, another night*): unchanged in meaning. It becomes
  a plain-language action with feedback (§8).
- **Open**: unchanged, with feedback (§8).
- **Placement** (one entry per screen at most, per principle 6): S4.R4.

### Q3 — Unsaved plans (UX-12, W1, V3)

| | U1 — keep the guard, make it complete (**recommended**) | U2 — list unsaved plans in Sessions ("Not saved") |
| --- | --- | --- |
| **Replacing a plan with unsaved changes** | Asks: **Save** · Discard · Cancel. It adds "Save", so the safe choice is one tap | Never asks; the old plan stays listed |
| **Discard** | Deletes the discarded draft: an honest "discard", no invisible leftovers | — |
| **An untouched draft** (the unedited new plan) | Deleted when replaced; nothing the user made is lost | Hidden or listed |
| **The Logbook** | Holds only intended (saved) sessions, which fits RG-04 | Mixes intended and abandoned exploration; needs a cleanup rule |
| **W1, V3** | Both count as unsaved, consistently: a Duplicate is a new, unsaved plan, and **a site change on a saved plan is an edit**, as its stored state already says | Moot |

The two are not exclusive. U1 is the smaller change, and it keeps the Logbook meaningful.

### Q4 — Identity and state in the planner (UX-04)

- **Recommended:** the app bar names the plan and the night, for example "M42 · Fri 14 Nov",
  with the state beside it: "Not saved", "Saved" or "Saved · changed". This matches the wireframe.
- Save's feedback names where it went. The exact words are RD-14's (S4.R5): "Logbook" or "Sessions"
  is still undecided, and today's "Session saved to Logbook!" is replaced then.
- No alternative is proposed: without it, principle 8 and the accepted wireframe are not met.

### Q5 — Yesterday's saved plan, the next day

## 6. Low-fidelity flows (recommended)

```text
FIRST RUN
  Welcome: 1 Site [choose]  2 Rig [choose/add]  3 Target [choose / What can I image?]
  → Planner "— · Tonight · Not saved"; capture plan empty [Start from the example plan]

PLAN AND SAVE
  Planner "M42 · Fri 14 Nov · Not saved" → edits autosave (still "Not saved")
  → [Save] → "M42 · Fri 14 Nov · Saved"  (snackbar names the Logbook/Sessions — wording S4.R5)
  → edit → "Saved · changed" → [Save] → "Saved"

NEW / DUPLICATE (plan has unsaved changes)
  [New] → "Unsaved changes: [Save] [Discard] [Cancel]"
        Save → saved, then new plan;  Discard → old draft deleted, new plan;  Cancel → stay
  New plan: same site and rig, target to choose, capture plan per Q6 → "Tonight · Not saved"
  [Duplicate for another night] → pick night → "M42 · Sat 15 Nov · Not saved" + snackbar

THE NEXT DAY (RG-04)
  Launch → last night's saved plan stays on its night, awaiting a result
         → Tonight: "Last night: M42. How did it go?"  (S4.R4 places it)
         → Planner: "M42 · Sat 15 Nov · Not saved" (a copy for tonight; Y2)
  Logbook entry → [Record result] → Completed as planned / Partly / Not done (RG-04)
```

## 7. Recommended direction

**L1 + n2 + U1 + the Q4 display + Y2 + the Q6 defaults.**
- **It keeps one meaningful commitment point (Save), which RG-04's Logbook needs, and removes the
  "Draft" stage the owner questioned** (O3).
- **It makes loss impossible without the user choosing it** (Save, Discard or Cancel). It
  resolves W1 and V3 consistently, and it stops leaving invisible drafts in storage.
- **It supports how imagers actually work:** the same rig night after night, one target over
  several nights (Y2's copy, and Progress).
- **It stops presenting unmade choices as made** (UX-24, ENG-15, SCI-12). The example plan stays
  one tap away, which answers 08 §14 without removing a teaching aid.
- **Data model:** unchanged except one ADR-014 rule (Y2: which session is resumed as current).
  Discarding deletes a draft the user discarded.

## 12. Validation correction: the complete saved-plan rule (S4.V1)

S4V-01 found that Q5's proposed `planned` exception did not cover a saved plan edited back to
`draft`. The owner requested the gap be fixed. **ADR-019 §3.1 is the normative state matrix.**

- A never-saved draft (`draft`, no `plannedAtUtc`) can roll forward in place. Both a saved
  `planned` entry and `draft` with `plannedAtUtc` are protected from automatic re-dating.
- Check the last explicitly saved night's bounds from its snapshot, not the mutable working
  site/date or the device date. Missing saved context means preserve and report unavailable,
  never guess. This applies at startup and while the application stays open.
- Stage 6's P6.7 protects both saved states in place. Stage 8's P8.3 adds an unsaved continuation
  from the working inputs for tonight. The original keeps its saved night/snapshot and any
  unsaved edits. Copy/adoption follows autosaves, survives restart/failure, and does not duplicate
  a continuation already adopted. No result or implicit Save occurs at rollover.
- Explicit Open of the historical entry is a review operation, not automatic resume. It
  preserves its working date and displays the saved night if different.
- Results for Saved · changed require **Review plan** (then explicit Save) or **Cancel**.
  The explicit Save refreshes that entry's snapshot under the existing ADR-014 rule. Only then
  does the result form use that saved version. Cancel/failed Save preserves both versions;
  later edits invalidate a stale result form and require review again. Rollover protection
  never depends on pressing Save again.
- Future acceptance covers Save → edit → next night on restart and without restart, including
  a changed working site/date, missing snapshot, pending writes and a repeated restart. It
  verifies both versions remain intact and result counts use the explicitly reviewed version.

This clarifies Y2 and its interaction with L1, not a new autosave model. Stage 4 remains
documentation only. The original options and decision record above remain historical evidence.

## 13. The owner's R2 + D1 (S4.V2)

The revalidation after S4.V1 failed (S4R-01, S4R-02; `../STAGE_4_REVALIDATION.md`). The owner then
decided (DECISIONS E.1, "S4R-01 and S4R-02 decided"). **ADR-019 §3.1, as revised, is normative.**
- **Y2, made precise:**
  - a saved plan's snapshot is the immutable intent for its night;
  - later edits are working-copy state;
  - the result is reported against the snapshot, without Save plan, and only after that night
    ends.
- **The next day, from Stage 8:** the saved entry stays on its night. The planner continues on one
  independent working copy. A working night that has not ended is kept; otherwise the copy takes
  tonight.
- **Delivery (D1):** Stage 6 changes only never-saved drafts and working plans. Saved plans keep
  today's behaviour until Stage 8 delivers the saved night and the working copy together.
- **U1's Discard** never deletes a saved entry. On Saved · changed it reverts only the working
  changes.
